1. Introduction

1.1 Purpose

This document captures the high-level requirements for Courseforge, a macOS desktop application that lets a solo course creator produce a complete online video course inside a single tool — from initial ideation through recording, editing, and export.

The SRS is intentionally vision-level. It exists to (a) establish shared understanding of what the product is and is not, and (b) act as a feature menu from which individual features will be peeled off and given their own detailed design documents prior to implementation.

1.2 Scope

Courseforge is a creation tool. It produces the artifacts of an online course (video files, transcripts, captions, and a structured manifest describing the course) and hands them off to the user. It does not host the courses, serve them to students, handle payments, track student progress, or otherwise behave as a Learning Management System.

The user takes the exported artifacts and publishes them wherever they wish — YouTube, Vimeo, Teachable, Thinkific, a private S3 bucket, etc. Direct upload integrations to those destinations are an explicit v-next goal, not a v1 requirement.

1.3 Intended Audience

This document is written for the project owner and any future contributors (engineers, designers, AI coding agents) who need a stable description of the product to work against. It assumes a software-engineering reader; it does not assume domain expertise in video editing or LMS conventions.

1.4 Conventions

  • Requirements are identified FR-X.Y.Z (functional) or NFR-Y (non-functional).
  • The keyword must denotes a v1 requirement.
  • The keyword should denotes a v1 recommendation that may slip if necessary.
  • Inline tags v1 and v-next flag which release a requirement belongs to.
  • "v-next" is shorthand for "after v1" — it is not a single planned release, just the bucket of named-but-deferred work.

2. Product Overview

2.1 Vision

A single macOS app where a course creator can sit down, brainstorm a course with AI, record every video in it, edit those videos surgically by editing their transcripts, polish them with effects, and export a publish-ready bundle — without ever uploading anything to a third party along the way.

The app treats the course (not the individual video) as the primary unit of work, and treats the user's local disk as the only place their work lives.

2.2 Target Users

The primary user is a solo course creator: an individual producing a structured video course for sale or distribution. They are typically subject-matter experts rather than professional video editors. They are comfortable installing desktop software and bringing their own API key for AI features.

Examples of the kind of course a primary user might produce: a guitar instruction course, a programming language tutorial, a yoga series, a corporate-skills training set.

2.3 Product Values

The following values should be considered when resolving any design tradeoff during implementation:

  • Local-first. No accounts, no telemetry, no required cloud services. The user's content lives on their disk and stays there until they choose to publish it.
  • Bring-your-own-key. Any AI features call providers using credentials the user supplies. Courseforge never proxies AI calls through its own servers and never charges the user for AI usage.
  • End-to-end in one tool. The user should not need a separate app to record, edit, or transcribe. Switching tools mid-flow breaks creative momentum.
  • Crash-resilient by default. Long recording sessions and in-progress edits must survive an unexpected crash without data loss.
  • Portable artifacts. A course is a self-contained folder on disk that the user can copy, zip, back up, or move to another Mac with no special export step.

3. System Context

3.1 Platform & Stack

  • Platform: macOS only (v1). No Windows or Linux support is planned.
  • Application framework: Tauri, with the application core written in Rust.
  • Persistence: Local filesystem. No required network services. No bundled server.
  • Credentials: AI provider keys are stored in the macOS Keychain.
  • OS integration: Recording is implemented in-process via Rust↔Objective-C bindings to ScreenCaptureKit (screen, individual windows, system audio) and AVFoundation (camera, microphone), writing one AVAssetWriter output per source so that every captured Source Role lands in its own file. The shared CMSampleBuffer clock guarantees frame-accurate cross-source sync. The app must request and respect the relevant macOS permissions (Screen Recording, Camera, Microphone).

3.2 Course Data Model

The conceptual hierarchy is intentionally shallow:

  • A Course contains an ordered list of Modules and a course-wide list of reusable Scenes (capture presets).
  • A Module contains an ordered list of Videos.
  • A Video is a multi-track timeline. It contains an ordered list of Tracks (video or audio); each Track holds Clips; each Clip references one Segment on disk and carries non-destructive placement and property values (position, scale, opacity, audio gain). Cuts on the Video timeline ripple across every overlapping Clip. Transcript decisions and effects layer on top.
  • A Segment is a single source's contiguous recording — one media file produced by one capture device or stream during one recording session. A multi-source recording session produces N peer Segments grouped by a shared Take id.

This two-level course hierarchy (Course → Module → Video) is fixed for v1. Deeper nesting (sub-modules, sections, lessons) is explicitly out of scope; users who need finer grouping can use additional top-level Modules. A richer hierarchy may be revisited later if real usage demands it.

3.3 Workflow Phases

A solo creator's work on a Video moves through four named phases. The UI surfaces them as distinct modes so the user always knows what they're doing. The phases are conceptual — every functional requirement in §4 sits in one of them.

  • Planning. Shaping the Course skeleton — Modules, Videos, titles, workflow state. No media exists yet. Covers FR-1.x, FR-2.x, FR-4.x.
  • Capture. Producing Segments by recording, with a Scene selecting which sources to capture and how they're initially laid out. Ends when the user keeps an N-source Take. Covers FR-3.x.
  • Assembly. Laying out captured Segments onto the Video's multi-track timeline. Auto-applied on Keep: the Scene's layout decides which Track each Segment lands on, where in time, and with what initial position / scale / opacity / audio gain. The user nudges from there.
  • Editing. Refining a Video that's already assembled — transcript-driven cuts, per-Clip property tweaks, effects, export. Cuts and edits never modify Segments on disk. Covers FR-5.x, FR-6.x, FR-7.x.

4. Functional Requirements

4.1 Course Library & Skeleton

  1. FR-1.1

    The app must open to a library view that lists all of the user's courses with their titles and basic status (e.g., last modified, video count).

  2. FR-1.2

    The user must be able to create a new course, open an existing course, rename a course, and delete a course.

  3. FR-1.3

    A course must be persisted as a self-contained folder on the user's disk, containing all of its videos, transcripts, project state, and metadata. Copying this folder elsewhere must produce a fully usable course on import.

  4. FR-1.4

    Within an opened course, the user must be able to view, add, rename, reorder, and delete Modules and Videos.

  5. FR-1.5

    The app should support having multiple courses open simultaneously (multi-window).

4.2 AI Ideation

  1. FR-2.1

    The user must be able to generate a proposed course skeleton (Modules and Video titles) from a high-level prompt describing the course they want to make.

  2. FR-2.2

    The user must be able to review, accept, edit, or regenerate the AI-proposed skeleton before it becomes their working course structure.

  3. FR-2.3

    All AI calls must use the user's own API key (bring-your-own-key). The key must be stored in the macOS Keychain and never transmitted to any Courseforge-operated service.

  4. FR-2.4

    v1 must support at least one AI provider (target: Anthropic / Claude). The implementation should be structured so that additional providers can be added later without a rewrite.

  5. FR-2.5

    If the user has not configured an API key, AI ideation features must degrade gracefully — the app remains fully usable for manual course creation, recording, and editing.

Multi-provider AI (OpenAI, Gemini, local models), and a persistent AI chat panel for ongoing refinement of an existing course, are explicit v-next goals.

4.3 Recording

  1. FR-3.1

    The user must be able to select a specific Video slot in the course skeleton and start a recording session that captures into that slot.

  2. FR-3.2

    A recording session must be able to capture any number of sources concurrently, drawn from a closed set of Source Roles: screen (a whole display), window (a specific app window), camera (any AVCaptureDevice, including built-in, USB, and Continuity Camera), microphone, and system_audio. Multiple sources of the same Role (e.g., two cameras) are permitted.

  3. FR-3.3

    Each captured source must be written to its own file on disk, with a sidecar JSON carrying its Source Role, the device identity, the capture wall-clock start, the shared Take id grouping the N peer Segments from one Record press, and the Scene-derived initial placement values.

  4. FR-3.4

    Cross-source sync must be frame-accurate — all sources in a Take share the macOS system clock at capture so that no per-source drift is introduced.

  5. FR-3.5

    A single Video may contain multiple recorded Takes (e.g., a re-take, an inserted screencast, an outro recorded separately). When a Take is kept, its Segments must be auto-arranged onto the Video's Tracks by Source Role: each new Segment appends to the matching Track at the end of the Video's existing timeline, creating a new Track if no matching one exists. The user can reorder, retime, or move Clips after the fact.

  6. FR-3.6

    The user must be able to define and save Scenes at the Course level — named, reusable presets that bind specific devices to Source Roles and define each source's initial position, scale, opacity, and audio gain on the Video frame. A Video may pin a default Scene; hitting Record uses that Scene, and the user may swap via "Record with…".

  7. FR-3.7

    Exactly one source per Scene must be markable as the Transcript Source. Only Segments produced by sources so marked are sent to transcription.

  8. FR-3.8

    Start must be atomic across all sources in the Scene: if any source fails to initialise (device missing, permission denied, content filter rejection), the entire Take aborts and any partial outputs are cleaned up. Mid-recording failure of one source must drop that source while the rest continue; the failed source's sidecar records the failure point.

  9. FR-3.9

    The user must be able to pause and resume a Take (atomic across all sources), and to discard or keep the Take at the end. Keep and Discard apply at the Take level — one decision applies to every Segment in the Take.

  10. FR-3.10

    A Take that did not survive a clean stop (app or OS crash mid-capture) must be recoverable on next launch. The app discovers orphaned outputs by Take id, groups them as a single Take, and offers Import or Discard for the whole Take.

  11. FR-3.11

    The app must surface clear, actionable feedback when a recording cannot start because of a missing macOS permission (Screen Recording, Camera, or Microphone), and must deep-link to the relevant Privacy & Security pane.

4.4 Workflow Tagging

  1. FR-4.1

    Each Video must carry exactly one workflow state at any time (e.g., Needs Recording, Needs Editing, Needs Intro, Needs Uploading).

  2. FR-4.2

    The set of workflow states must be defined by the user as a personal preference. The user must be able to add, rename, reorder, and remove states. The app ships with a sensible default set the user can replace.

  3. FR-4.3

    The user must be able to see all videos in a course grouped by workflow state (kanban-style board view) and move videos between states.

  4. FR-4.4

    Workflow transitions are manual only in v1. The app does not automatically advance a video's state based on recording or editing activity.

Automated workflow transitions (e.g., a Video that has been recorded automatically moves from Needs Recording to Needs Editing) may be revisited once real workflow patterns emerge.

4.5 Transcript-Based Editing

  1. FR-5.1

    The app must automatically generate a transcript for each recorded Video, with word-level timestamps.

  2. FR-5.2

    The user must be able to view the transcript synchronised with the video, with the active word highlighted during playback.

  3. FR-5.3

    The user must be able to select text in the transcript and remove the corresponding audio and video. Selection granularity must support both individual words and whole sentences (e.g., a sentence-select convenience action).

  4. FR-5.4

    All transcript-driven edits must be non-destructive: the original recorded Segments are never modified. Edits are stored as a list of cut/keep decisions and applied at playback and at export time.

  5. FR-5.5

    The app must support unlimited undo and redo of transcript-driven edits within an editing session.

  6. FR-5.6

    Transcripts must be persisted alongside their Videos as part of the course folder, so they remain available for re-editing, search, and caption export without re-running transcription.

  7. FR-5.7

    Transcripts must be stored per-Segment in the Segment's own source-time, and the Video-timeline view must be derived at read time from the current Clip placements (start, in-point, out-point, and active Cuts). Moving, retiming, or splitting Clips in Assembly does not require re-running transcription.

  8. FR-5.8

    Only Segments captured by a source marked as the Transcript Source on the Scene used to produce the Take must be transcribed. Captured audio from other sources (e.g., system_audio, a second mic not so marked) is excluded.

4.6 Effects & Plugins

  1. FR-6.1

    The app must ship a built-in library of video and audio effects covering common course-production needs. The exact set is scoped per-feature, but the intended coverage includes: skin smoothing, cursor zoom and highlight, transitions between segments, lower-thirds and text overlays, color filters / look adjustments, and background music with ducking.

  2. FR-6.2

    Effects must apply non-destructively as part of the Video's edit decision list and be re-orderable, adjustable, and removable.

  3. FR-6.3

    The effects architecture should be designed with future third-party plugin support in mind. v1 does not ship a public plugin API.

  4. FR-6.4

    Per-Clip composition properties — position, scale, opacity, visible, and audioGain — are first-class non-destructive edit values, distinct from Effects. They are constant per Clip in v1 (no keyframes); changes are persisted to the EDL via the same atomic append-and-replay mechanism as transcript-driven cuts. scale is canvas-relative (1.0 fills the Video's output frame); audioGain is expressed in dB (range −∞ to +12 dB, with 0 dB = recorded level).

Third-party plugin support via an industry-standard host-agnostic video plugin format (target: an OpenFX-style standard, analogous to VST3 in audio) is an explicit v-next goal. v1 builds the in-app effect pipeline in a way that makes adopting such a standard later realistic. Keyframable composition properties (animating position/scale/opacity/audioGain over time) are also v-next; v1 carries a single constant value per Clip.

4.7 Export

  1. FR-7.1

    The user must be able to export each Video as a finished MP4 file with all transcript-driven edits and effects applied.

  2. FR-7.2

    The user must be able to export the whole Course as a bundle: the MP4 files organised on disk by Module and Video order, plus a manifest (JSON and/or CSV) describing the course structure, titles, descriptions, and per-video metadata. This bundle is intended to make bulk upload to an LMS less painful.

  3. FR-7.3

    Each exported Video must have an accompanying .srt caption file derived from the (edited) transcript. The user should additionally be able to choose to burn captions into the video.

  4. FR-7.4

    The user must be able to preview an individual Video (with all edits and effects applied) inside the app before exporting it. The preview and the export must render through one shared composition model so that what the user sees in the editor is what lands in the exported file.

  5. FR-7.5

    Each Course must define a single output canvas (resolution and frame rate) used by every Video in the Course. The default is 1920×1080 at 30 fps; the user may change it in Course settings. Per-Clip scale and position values are interpreted in this canvas's coordinate space.

A whole-course preview / playthrough mode (watching the course end-to-end inside the app), and direct upload integrations to YouTube, Vimeo, Teachable, and similar destinations, are explicit v-next goals. SCORM, xAPI, and Common Cartridge LMS-export formats are out of scope unless a corporate-training audience becomes a stated target.

5. Non-Functional Requirements

  1. NFR-1

    Local-first. No Courseforge-operated server is required for any feature listed in §4. The app must function fully offline once installed (with the obvious exception that AI ideation calls reach the user's chosen AI provider over the internet).

  2. NFR-2

    Privacy. The app collects no telemetry, analytics, or usage data by default. The user's recordings, transcripts, prompts, and edits are never transmitted off-device except (a) to the AI provider the user has configured, when the user explicitly invokes an AI feature, and (b) to destinations the user explicitly chooses at export time.

  3. NFR-3

    No required account. The user can install the app and use every v1 feature without creating an account on any service. (They do need an AI provider account of their own to use AI ideation.)

  4. NFR-4

    Crash resilience for recordings. If the app or OS crashes during a recording, the captured-so-far audio and video must remain playable and importable into the originating Video slot when the app is reopened.

  5. NFR-5

    Crash resilience for edits. Transcript edits and effect adjustments must be persisted incrementally so that an unexpected exit does not lose more than the user's most recent action.

  6. NFR-6

    Portability. A course folder must be self-contained — no external references, no machine-specific absolute paths in the project files. Copying the folder to another Mac running Courseforge must reproduce the course faithfully.

  7. NFR-7

    Keyboard-driven editing. The editing UI must support standard video-editor keyboard transport (e.g., JKL for shuttle, spacebar for play/pause) and provide keyboard shortcuts for the common transcript-edit operations.

  8. NFR-8

    Performance. The app must remain responsive on a current-generation Apple Silicon Mac when working with a course of typical size (target: a multi-hour course composed of 30+ videos, each up to ~30 minutes long, recorded at 1080p). Specific latency and memory budgets are deferred to per-feature design.

  9. NFR-9

    macOS permissions. All required macOS permissions (Screen Recording, Camera, Microphone, file access) must be requested at the point of use with clear in-app messaging explaining why they are needed.

  10. NFR-10

    Accessibility. The UI should follow macOS accessibility conventions (VoiceOver labels on controls, sufficient contrast, full keyboard navigability of non-timeline UI). Detailed accessibility requirements are deferred to per-feature design.

6. Out of Scope (v1)

To keep v1 focused, the following are explicitly not included. Each is either deferred to v-next (see §7) or out of scope entirely.

  • Hosting, streaming, or serving courses to students.
  • Student authentication, enrollment, progress tracking, certificates, payments, or any other LMS functionality.
  • Windows, Linux, iOS, iPadOS, or web/browser versions of the app.
  • Real-time collaboration or multi-user editing.
  • Server-side AI services operated by Courseforge.
  • SCORM, xAPI, Common Cartridge, or other corporate-LMS export formats.
  • Hierarchical course structures beyond Course → Module → Video.

7. v-next Roadmap

The following are named, deferred goals. They influence v1 architecture decisions (so that adopting them later is realistic) but are not v1 requirements.

  • Keyframable composition properties — animating per-Clip position, scale, opacity, and audio gain over time (v1.5 carries a single constant value per Clip).
  • Per-source Keep / Discard at the end of a Take, so the user can drop a bad angle without retaking. v1.5 resolves this in the editor by deleting unwanted Tracks.
  • Media Bin — a per-Video library of captured Segments separate from the timeline, useful once external media (drag-in of an existing MP4) becomes a flow.
  • Source Monitor — setting in/out points on a Segment before placing it on the timeline.
  • Lift cuts — removing a span from the timeline without rippling the downstream Clips left. v1 cuts are always ripple.
  • Linked Selection management UI — surfaced control of which Clips are linked beyond the default takeId-based linking (e.g., manual link of unrelated Clips, save/restore link groups).
  • Markers and chapters on the Video timeline.
  • Multicam editor — a dedicated view for switching between camera angles of the same Take during editing.
  • Persistent AI chat per course — an ongoing conversation that can read and modify the course skeleton.
  • Multi-provider AI — OpenAI, Gemini, local models, in addition to Anthropic.
  • Third-party effect plugins via an industry-standard host-agnostic format (target: OpenFX-style).
  • Direct upload integrations — YouTube, Vimeo, Teachable, Thinkific, and similar destinations.
  • Full-course preview — end-to-end playback inside the app before export.
  • Automated workflow transitions based on recording / editing activity.
  • Sub-modules or deeper hierarchy, if real usage patterns demand them.

8. Glossary

Course
The top-level unit of work. An ordered collection of Modules, persisted as a self-contained folder on disk.
Module
A named, ordered grouping of Videos within a Course (e.g., "Introduction", "Mechanics", "Theory").
Video
The exportable unit. A timeline composed of one or more recorded Segments plus non-destructive edit and effect decisions.
Segment
A single source's contiguous recording — one media file produced by one capture device or stream during one recording session. A Video references its Segments through Clips on Tracks; multi-source recording produces N peer Segments per Take.
Take
The N peer Segments captured together in one Record press, sharing a Take id and a wall-clock start. Take is the unit of Keep/Discard, orphan recovery, and default Clip linking in the editor.
Source Role
What a Segment is a recording of. Closed at five values: screen, window, camera, microphone, system_audio. Carried in each Segment's sidecar; multiple-of-the-same-Role per Take is permitted.
Scene
A named, reusable capture preset at the Course level — an ordered list of Source Roles bound to specific devices, plus each source's initial composition properties on the Video frame. A Video can pin a default Scene; the Scene's layout is what auto-arranges captured Segments at the start of Assembly.
Track
A persistent row on a Video's timeline that holds one or more Clips. Tracks have a kind (video or audio), an order, and per-Track metadata (name, lock, solo, mute).
Clip
A placement of a Segment on a Track — carrying placement (startOnTimeline, inPoint, outPoint) and composition properties (position, scale, opacity, audioGain, visible). Multiple Clips may reference the same Segment.
Linked Clips
Clips sharing a Take id are linked by default — selecting or moving one moves all, preserving the frame-accurate sync captured at recording. The user can explicitly Unlink when they want to drift sources apart.
Cut
A time range on the Video's assembled timeline that is dropped at render time, ripple-style — downstream Clips slide left to close the gap. A Cut applies to every Clip overlapping its span.
Workflow state
A user-defined label indicating where a Video is in the creator's personal production process (e.g., Needs Recording, Needs Editing).
Transcript
An automatically generated text representation of a Video's spoken content, with word-level timestamps. Persisted with the Video.
Transcript-based editing
Modifying the Video by editing its transcript: selecting words or sentences and removing them, which removes the corresponding audio and video.
Non-destructive editing
Editing in which the original recorded files are never modified. Edits are stored as decisions and applied at playback and at export.
Effect
A non-destructive visual or audio transformation applied to a Video (e.g., skin smoothing, cursor zoom, lower-third, music ducking).
BYOK
Bring-your-own-key. The user supplies their own AI provider API credentials; Courseforge never proxies or charges for AI usage.
MKV
Matroska container format. Historical: used by the v1 ffmpeg-child recorder as a crash-resilient intermediate before remux to MP4. Superseded by direct AVAssetWriter .mov output once the in-process ScreenCaptureKit recorder lands (see ADR-0002); existing v1 Course Folders with .partial.mkv orphans remain importable.
MP4
The export container format. Used because it is the universally accepted format for downstream platforms (YouTube, LMSs, etc.).
v-next
Shorthand for "after v1." Used to mark named goals that are deferred but considered in v1's architecture.
